# Черновик переносимости Wterm Terminal Preview

Этот документ фиксирует текущее состояние на случай, если терминал потребуется перенести из BB в другое веб-приложение, IDE, Electron-приложение или плагин.

Это предварительная архитектурная оценка, а не обязательство по roadmap.

## Краткая оценка

- **Переносимость текущего плагина как готового артефакта: 2/10.**
- **Лёгкость переноса в другой хост: 4/10.**
- **Переиспользуемость одного терминального UI и Ghostty-рендерера: около 6/10.**

Плагин нельзя установить в другую IDE или веб-приложение без адаптации. Однако его терминальный UI и часть клиентской логики можно выделить в самостоятельный пакет и подключать к разным источникам PTY-потока.

## Что уже можно переиспользовать

Относительно независимы от BB:

- Ghostty WASM через `@wterm/ghostty`;
- React-рендерер через `@wterm/react`;
- базовый контракт `TerminalAttachment` с операциями `subscribe`, `sendInput`, `sendResize` и `detach`;
- обработка OSC 52 и clipboard;
- выделение и копирование текста;
- retryable cache;
- часть логики состояния терминала и выбора сессии.

Эти компоненты можно использовать в другом React-приложении, если новый хост предоставит терминальный поток, ввод и resize.

## Что сейчас привязано к BB

Основные точки сцепления:

- регистрация UI через `definePluginApp` и `@bb/plugin-sdk/app`;
- контекст thread и панели BB;
- создание, получение и перезапуск PTY через `bb.sdk.terminals`;
- хранение связанных терминалов в BB KV;
- поток вывода через `/ws/terminals/:id` и BB-специфичный replay/sequence-протокол;
- RPC и загрузка WASM, шрифта и файлов через `/api/v1/plugins/wterm-terminal-preview/...`;
- запись файлов через `bb.sdk.files`;
- plugin token и проверки принадлежности терминала BB thread;
- экспериментальные API BB для вкладок и claimed terminal.

Без этих возможностей BB текущий плагин не создаёт терминальную сессию и не получает её поток.

## Черновик возможного переноса

Если перенос действительно понадобится, разумно разделить систему на три слоя.

### 1. Portable renderer

Самостоятельный пакет без зависимости от `@bb/plugin-sdk`:

- `@wterm/react` и `GhosttyCore`;
- terminal grid и стили;
- keyboard, mouse, resize и selection;
- clipboard/OSC 52;
- настройка шрифта;
- загрузка WASM и шрифта через передаваемые URL или loader-функции.

### 2. Terminal transport

Универсальный контракт подключения:

```ts
interface TerminalTransport {
  subscribe(listener: (chunk: Uint8Array) => void): () => void;
  sendInput(bytes: Uint8Array): boolean;
  resize(cols: number, rows: number): boolean;
  detach(): void;
}
```

Конкретный хост реализует WebSocket, replay, reconnect, авторизацию и управление PTY. Текущий BB-класс `LegacyTerminalAttachment` становится одной из таких реализаций.

### 3. Host adapters

Отдельные тонкие оболочки:

- BB plugin;
- обычное веб-приложение;
- Electron/Tauri;
- VS Code webview;
- Obsidian или другой plugin SDK.

Каждая оболочка отвечает только за создание сессии, авторизацию, вкладки, upload и интеграцию с API своего хоста.

## Что придётся написать для нового хоста

Минимально необходимы:

1. PTY-сервис или доступ к существующему PTY API.
2. Двунаправленный транспорт вывода, ввода и resize.
3. Авторизация WebSocket/HTTP.
4. Жизненный цикл create, attach, detach и restart.
5. Host-specific UI для вкладок или выбора сессий.
6. Отдельный файловый API, если нужен upload.

Сам Ghostty-эмулятор и большую часть рендеринга переписывать не нужно.

## Предварительный вывод

Сейчас Wterm Terminal Preview — **BB-плагин с потенциально переносимым внутренним renderer-слоем**, а не универсальный terminal SDK.

До появления реального второго хоста не стоит заранее строить сложную платформу адаптеров. Если перенос станет задачей, первым вертикальным шагом следует вынести renderer и transport contract без BB-зависимостей, после чего реализовать один конкретный второй host adapter и проверить архитектуру на реальной интеграции.
