# Wterm 0.5.0: установка, dev-режим и задачи

## Почему версии расходились

Коммит `c864fdc` от 5 сентября 2026 закрепил `@wterm/dom`, `@wterm/react` и `@wterm/ghostty` на `0.5.0` в манифесте и lockfile. Установленные пакеты оставались `0.4.0`: `npm ls` завершался с `ELSPROBLEMS`. Метаданные локальных пакетов датированы 4 сентября, то есть старше обновления манифеста. Установка не была приведена в соответствие с новым lockfile; кто и какой командой оставил это состояние, не установлено.

Дополнительная причина путаницы: BB использовал отдельный checkout:

```text
/home/ubuntu/.bb-server/worktrees/env_8bc3fyvjm7/bb-wterm-terminal-plugin
```

Проверенные исходники, manifest/lock, WASM и `dist/app.js` там совпадали с текущим репозиторием, а установленные пакеты также были `0.4.0`. Совпадение bundle с локальным `dist` не означало, что BB был настроен именно на локальный путь.

- `npm ls @wterm/core @wterm/dom @wterm/react @wterm/ghostty`: exit 0, все 0.5.0, без invalid.
- Быстрый LSP-вызов по трём файлам первоначально вернул 0 ошибок. Однако итоговый session-wide scan показал **53 предупреждения** в `terminal-panel.tsx` и `wterm-renderer.tsx`: преимущественно inferred project без tsconfig и React/SDK declarations. Полная типовая чистота **не подтверждена**. Проверка реальных дефектов, включая `toast` без импорта в error-path `terminal-panel.tsx:222/230`, добавлена в блокирующую задачу `.13`; это не следует автоматически считать шумом или регрессией Wterm 0.5.0.
- `npm test`: 14 файлов, **120 тестов прошли**, 991 мс.
- `npm run build`: успешно. Это проверка совместимости, не доказательство ускорения.
- Реальный браузер: новая отдельная sidebar Wterm-сессия, ввод `printf 'WTERM_050_SMOKE_OK\n'`, точная строка ответа появилась в DOM, 27 terminal rows; page errors отсутствуют.
- Served JS совпал по SHA-256 с новым `dist/app.js`: `5689b07dd31a7d8afc2a1753a9a16130c30d6546d4d09d0d8f14c4049860cab5` для dev-артефакта этого прогона.

Не заявлялась полная проверка TUI, clipboard permissions, Kitty graphics, upload и p95. Они включены в Beads. Старые performance-цифры в `PERFORMANCE-ANALYSIS-2026-09-06.md` остаются историческим baseline несогласованной установки, а не результатом 0.5.0.

## BB и dev-сервер

Работающий сервер уже существовал: `http://127.0.0.1:38896`, host daemon port `38897`. Второй BB-сервер не запускался, существующий не перезапускался.

Команда `bb plugin install path:/home/ubuntu/Projects/bb-wterm-terminal-plugin --yes` перенесла **path-source** плагина на текущий репозиторий. BB подтвердил сохранение settings, secrets и schedules. Старый checkout не удалялся и не изменялся.

Для проверки источника:

```sh
BB_SERVER_URL=http://127.0.0.1:38896 BB_HOST_DAEMON_PORT=38897 \
  bb plugin source wterm-terminal-preview
```

Для dev-режима используется global `bb plugin dev` с тем же явно указанным endpoint. Watcher запускает rebuild/reload, не отдельный HTTP frontend server. Его живой stdout должен быть **вне наблюдаемого репозитория**: запись в `.logs/dev-server.log` вызвала повторные rebuild/reload. Старый лог сохранён; текущий путь, PID и контроль тишины фиксируются в `.logs/wterm-dev-runtime.json` и комментарии Bead `wterm-a4b.2`.

Не запускать второй watcher одновременно. Для остановки сначала сверить PID и дочерний процесс из runtime-файла с актуальным `ps`; не использовать широкие `pkill bb` или остановку общего сервера.

## Оставшееся расхождение SDK

Манифест содержит SDK `0.4.21`. `npm run build` использует локальный `bb-app 0.38.0` и предупреждает о SDK сборщика `0.4.6`; global dev CLI предупреждает о `0.4.34`. Это разные tooling-поверхности, не версия Wterm.

При повторном запуске global watcher в 11:00 UTC свежий warning уже указывает SDK `0.4.47`. Значение `0.4.34` выше — историческое, а не текущая константа; каждую серию измерений нужно сопровождать фактическими версиями. Эта сессия SDK и общий BB не обновляла.

Согласование канонического CLI, SDK и build provenance вынесено в `wterm-a4b.13` и `.3`; baseline `.4` зависит от них, чтобы поздняя смена сборщика не обесценила сравнение.
