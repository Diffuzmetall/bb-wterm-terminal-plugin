# Анализ отзывчивости Wterm — 6 сентября 2026

> Исторический снимок до согласования установки. Позднее в тот же день установлены проверенные пакеты 0.5.0, повторно прошли 120 тестов и browser smoke. Причина drift, перенос активного BB path-source и текущие Beads описаны в [отчёте об установке](UPGRADE-WTERM-0.5.0-2026-09-06.md). Числа производительности ниже не являются замерами обновлённого стенда.

## Вывод

Ускорять нужно два разных участка: открытие панели внутри BB и восстановление/обработку потока терминала. В живом замере большая задержка возникла **до запроса создания терминала**. В локальном транспорте отдельно подтверждён квадратичный алгоритм восстановления истории. Переписывать весь рендерер или заменять Ghostty оснований пока нет.

Применён skill `extreme-software-optimization`: измерения → проверка причин → приоритеты, без реализации оптимизаций. Продуктовый код, зависимости, настройки BB и рабочие терминалы не изменялись. Для наблюдения дважды открывалась отдельная sidebar-панель Wterm; команды в неё не вводились.

## Область и ограничения

- Проверены текущие исходники, установленные пакеты, живой BB на `http://127.0.0.1:38896`, тесты, Chrome trace и отдельный синтетический replay-прогон.
- Браузер работает на сервере через loopback. Это **не** измерение сети/компьютера пользователя.
- Два открытия — отдельные наблюдения, не p50/p95. Второе выполнено с профилировщиком и содержит его накладные расходы.
- «Первые строки» означает появление `.wterm-renderer .term-row` в DOM, а не гарантированный paint готового shell prompt и не input-to-echo.
- Нагруженный TUI, реальные клавиши, reconnect с пользовательской историей и 10 одновременно открытых терминалов не профилировались. Нет оснований приписывать им полученные startup-цифры.
- Два read-only исследователя использовали `openai-codex/gpt-5.6-luna`. Переданный запрос `high` не применился: runtime сообщил `medium`. Soul/Sol не использовался. Результаты не принимались автоматически; ошибочное утверждение о блокирующей проверке `listSessions` отклонено при сверке с исходником.

В первом открытии наблюдались long tasks длительностью 150, 82, 136 и 122 мс; окно наблюдения продолжалось и после появления строк.

Наблюдение достаточно сильное, чтобы сначала расследовать переход/монтирование BB: быстрый backend не компенсирует 754 мс ожидания перед отправкой запроса. Но не все эти 754 мс автоматически относятся к CPU: нужны дополнительные воспроизводимые профили.

Сохранён Chrome trace: `.logs/performance-analysis-trace.json` (86,5 MiB). Скриншот: `/tmp/wterm-perf-analysis.png`. Trace может содержать внутренние URL и метаданные браузера; не публиковать без проверки.

### 2. Расхождение зависимостей

`package.json` и `package-lock.json` фиксируют `@wterm/dom`, `@wterm/react`, `@wterm/ghostty` **0.5.0**. Фактически все три установленных `node_modules/@wterm/*/package.json` содержат **0.4.0**.

Живой `assets/app.js` побайтно совпал с локальным `dist/app.js`:

- размер: 450 006 байт;
- SHA-256: `f28c249465d53975d26a669f459c2fd94c8df579610c44e844d63c86f6b6d344`.

Это связывает живой bundle с локальным артефактом, но само по себе не доказывает происхождение всех его зависимостей. Выводы о внутренностях пакетов ниже относятся именно к установленным **0.4.0**. Нельзя выдавать их за аудит реализации 0.5.0. В dev-log также есть предупреждение SDK 0.4.21 против SDK хоста 0.4.34; его актуальность надо повторно проверить при подготовке воспроизводимого build.

**Первый шаг перед исправлениями:** собрать из согласованного lockfile в отдельной среде, установить происхождение WASM и JS, повторить тесты и baseline. Не запускать автоматически `npm ci` или замену живых артефактов в работающем checkout.

### 3. Replay: подтверждён рост стоимости

Реальный `LegacyTerminalAttachment` импортирован в отдельный Node-процесс с type stripping, без WebSocket и без подключения к BB. Переданы `attached(nextSeq=N)` и N возрастающих output-sequence с однобайтовым payload. JSON-сообщения подготовлены до начала замера; доставка всех N фрагментов проверена. По три прогона на размер, предварительный прогрев на 100 фрагментах.

| Число фрагментов | Медиана | Диапазон трёх прогонов |
| ---: | ---: | ---: |
| 1 000 | 30 мс | 14–36 мс |
| 5 000 | 424 мс | 357–549 мс |
| 10 000 | 2 217 мс | 671–4 141 мс |
| 30 000 | 4 671 мс | 4 520–6 607 мс |

Это синтетический transport-only benchmark, **не** время открытия реального пользовательского терминала. Разброс велик; серверные условия не изолированы. Реальный размер replay-окна BB не установлен. Тем не менее квадратичная работа подтверждается непосредственно кодом, в том числе для уже отсортированного replay.

Воспроизведение из корня проекта, Node с поддержкой `--experimental-strip-types`:

```sh
node --experimental-strip-types --input-type=module <<'JS'
import { performance } from 'node:perf_hooks';
import { LegacyTerminalAttachment } from './terminal-attachment.ts';
function trial(n) {
  const a = new LegacyTerminalAttachment('offline-benchmark');
  let delivered = 0;
  a.subscribe(() => delivered++);
  const messages = Array.from({length: n}, (_, seq) => JSON.stringify({
    type: 'output', chunk: {seq, dataBase64: 'YQ=='}
  }));
  a.handleMessage(JSON.stringify({type: 'attached', nextSeq: n}));
  const start = performance.now();
  for (const message of messages) a.handleMessage(message);
  const elapsed = performance.now() - start;
  if (delivered !== n) throw new Error('lost replay');
  a.detach();
  return elapsed;
}
trial(100);
for (const n of [1000, 5000, 10000, 30000]) {
  const times = Array.from({length: 3}, () => trial(n)).sort((a,b) => a-b);
  console.log({chunks: n, medianMs: times[1], runsMs: times});
}
JS
```

Вызов TS-private `handleMessage` здесь — намеренный внутренний тестовый вход после удаления типов, не публичный API приложения.

### 4. Тесты

`npm test`: **14 файлов, 120 тестов прошли**, 1,32 с.

`vitest.config.ts` использует Node environment и SDK stub. Есть полезные проверки очередности, reconnect, resize, OSC 52, thread scope и настоящий WASM в `ghostty-init.test.ts`. Но DOM-интеграция и отзывчивость не измеряются. Часть проверок `wterm-renderer.test.ts` ищет строки в исходниках/CSS — например, наличие константы 250 мс — вместо проверки поведения с часами и реальным layout.

Зелёные тесты защищают часть корректности, но не доказывают быстрые клики. Они также прошли на текущей установленной среде 0.4.0, не на чистой установке lockfile 0.5.0.

## Приоритеты изменений

Оценка по skill: влияние × уверенность / трудозатраты, шкала 1–5. Оценки помогают выбрать эксперимент и не являются обещанием ускорения. Для гипотез сначала нужен подтверждающий профиль.

| Очерёдность | Участок | Оценка | Что делать |
| --- | --- | ---: | --- |
| 0 | Версии и build provenance | обязательный gate | Воспроизводимая отдельная сборка; не менять рабочий стенд вслепую |
| 1 | Переход/монтирование BB | 5×4/3 ≈ 6,7 | Разобрать задержку до `openWterm`, layout и работу других расширений |
| 2 | Replay в `terminal-attachment.ts` | 4×5/2 = 10 | Убрать повторные линейные проходы и сортировать один раз |
| 3 | Пакетная обработка потока | 4×3/3 = 4 | Измерить burst и, если подтверждено, обрабатывать очередь с бюджетом времени |
| 4 | Resize панели | 3×5/3 = 5 | Разделить первый usable resize и стабилизацию анимации |
| 5 | Scrollback DOM | 3×3/3 = 3 | Проверить на согласованной версии; затем исключить сборку неизменных строк |
| 6 | Списки и upload control plane | 2×4/2 = 4 | Уменьшить число lookup при больших списках, сохранив авторизацию |

### 1. Переход BB, жизненный цикл и холодный старт

- `herdr-panel.tsx:31–70`: `openWterm/openHerdr` выполняется в effect после монтирования; при размонтировании терминал закрывается. Следовательно, повторный вход в sidebar-панель может означать новый shell, attach и новый core, а не дешёвое переключение вкладки. Это текущая семантика, не повод автоматически сохранять процессы навсегда.
- `wterm-renderer.tsx:280–295, 451–476`: Blob с WASM кэшируется, но новый renderer получает новый core. `preloadTerminalAssets` прогревает загрузку, не готовый terminal instance.
- `wterm-renderer.tsx:297–323`: шрифт кэшируется через WeakMap для `document.fonts`. В профиле есть существенные samples в `FontFace`; точную долю CPU нельзя получить простым суммированием wall-time samples.
- `app.tsx:510–597`: thread-actions уже запускают preloading параллельно созданию терминала. Не добавлять второй такой же preload.

**Следующий эксперимент:** 20 повторов открытия/переключения в одинаковом сценарии; Performance marks для click, effect, request, WS attached, core-ready, replay-complete и первого paint. Отдельная BB-среда без вспомогательных overlay/debug-плагинов для контрольного сравнения. Не отключать их глобально без согласования.

После локализации: минимально устранить повторное монтирование/тяжёлую работу хоста либо перенести допустимый asset warmup раньше. Решение о сохранении sidebar-сессии при уходе требует отдельного согласования семантики.

### 2. Квадратичный replay

`terminal-attachment.ts:167–195`:

- `pendingReplay.some` ищет дубликат для каждого фрагмента;
- линейный поиск места вставки повторяется для уже отсортированных фрагментов;
- `flushWhenReplayComplete` снова делает `.some` после каждого сообщения;
- затем весь накопленный replay синхронно декодируется и доставляется.

**Минимальный вариант:** `Map<seq, chunk>`, O(1) проверки наличия завершающего seq, одна сортировка при готовности replay. Сначала сохранить существующую семантику ready-marker и порядка, отдельно решать возможность изменения протокола завершения replay. Не смешивать этот патч с заменой WebSocket.

Проверки: duplicate/out-of-order, live перед завершением replay, reconnect с уже доставленными seq, пустой replay, отмена, тот же байтовый поток на выходе. Затем повторить benchmark и browser reconnect. Оптимизация не должна выбрасывать ANSI/PTY-байты.

### 3. Burst output, очереди и свободный main thread

- `terminal-attachment.ts:86–90, 198–206`: накопленные данные перед подпиской передаются синхронно.
- `wterm-renderer.tsx:485–500, 673–685`: обычный write вызывается сразу; очередь до usable size полностью выгружается одним циклом.
- `node_modules/@wterm/dom/dist/wterm.js:146–175`: write синхронно передаёт данные core; RAF объединяет **отрисовку**, но не сам парсинг.
- `node_modules/@wterm/ghostty/dist/wasm-bindings.js:214–230`: цикл по 8 KiB с alloc/copy/write/free и drain-response между блоками.

**Сначала:** нагрузка фиксированного размера в отдельном тестовом терминале, запись long tasks и input-to-echo. Если парсинг занимает значительную долю окна, обрабатывать упорядоченную очередь с небольшим бюджетом времени, отдавая браузеру управление между порциями. Сохранить drain ответов, UTF-8/ANSI, synchronized output, OSC 52 и Kitty graphics.

Нельзя просто добавить RAF вокруг каждого write: это может добавить задержку одиночному символу и не ограничить длинную задачу. Нельзя обрезать очередь или терять ввод ради памяти. Для переполнения нужен явный backpressure/recovery-контракт с хостом.

### 4. Resize — явная задержка, но с защитной целью

`wterm-renderer.tsx:52, 729–770`: PTY resize отправляется спустя **250 мс после последнего** изменения usable grid. Комментарий связывает это с анимацией BB на 220 мс и защитой TUI от промежуточных SIGWINCH.

Возможный эксперимент: первый валидный размер отправлять сразу; анимируемое maximize/restore завершать по фактическому окончанию перехода с fallback timeout; обычный resize проверять отдельно. Не менять единый timeout на ноль.

Проверки: maximize/restore, перетаскивание границы, font change, скрытая вкладка 0×0/1×1, возврат к прежнему размеру, отсутствие дублированных кадров TUI.

### 5. Scrollback DOM

В установленной 0.4.0 `node_modules/@wterm/dom/dist/renderer.js:448–531` виртуализация уже есть. Однако при изменении диапазона/числа строк цикл строит candidate DOM для каждой видимой строки, затем сравнивает `innerHTML` и CSS с прежней строкой.

Гипотеза: при длинном потоке/прокрутке тратится время на повторную сборку неизменных строк. Проверить профиль `_buildScrollbackRowEl`, allocations и layout. Если подтвердится и сохранится в 0.5.0 — исправлять в отслеживаемом upstream-патче/версии по стабильной идентичности строки, а не вручную редактировать `node_modules`.

### 6. Лишние обращения при list/upload

`server.ts:277–312, 329–344`: список выполняет один legacy list и N `terminals.get` для связанных терминалов. Get идут параллельно через `Promise.allSettled`, поэтому это **не N последовательных RTT**, но запросов всё равно N. `resolveUploadTerminal` на `server.ts:346–370` повторяет общий поиск для thread upload.

Для текущего sidebar-startup это не главный измеренный тормоз. Проверять при 1/10/100 связанных терминалах. Возможное улучшение — targeted lookup с проверкой membership, дедупликация одновременных list-запросов. Не доверять session-объекту из браузера и не убирать thread authorization ради скорости.

## Что пока не делать

- Не заменять Ghostty/DOM на Canvas/WebGL/Worker без подтверждённого hotspot.
- Не добавлять виртуализацию и RAF с нуля: они уже есть в установленном Wterm.
- Не начинать с одного лишнего `isDirtyRow` на кадр или переиспользования `TextEncoder`: код это допускает, но влияние не измерено и существенно меньше подтверждённых кандидатов.
- Не объявлять Base64 главным тормозом и не переходить на binary WebSocket без профиля и согласованного host-протокола.
- Не убирать `listSessions` якобы из блокирующего render-gate: `SelectedTerminal` в `app.tsx:352–438` начинает со state `ready` и монтирует панель параллельно проверке. Утверждение исследователя об обязательном ожидании list было неверным.
- Не интерпретировать время dev rebuild из `.logs/dev-server.log` как задержку пользовательского клика.

## Критерии для следующего этапа

Предлагаемые цели, не текущие результаты:

1. Видимый feedback локальной кнопки: p95 до 50 мс; переключение уже готовой панели — до 100 мс.
2. Для печати отдельно учитывать WS RTT: измерять keydown → отправка, input → echo и echo → paint. Последний участок желательно удержать в пределах 1–2 кадров.
3. В репрезентативном output-burst не допускать длительных блокировок ввода; отслеживать задачи >50 мс и долю кадров >16,7 мс.
4. Измерять cold/warm open, 1/5/10 вкладок, reconnect, hidden-tab recovery, resize и большой scrollback отдельно. Не складывать их в одну метрику.
5. После каждого патча: прежний байтовый поток/порядок, smoke-test настоящего браузера, regression tests и before/after в одинаковой среде.

**Рекомендуемый первый срез:** согласовать версии в отдельном стенде, снять короткий воспроизводимый baseline открытия и replay, затем отдельно исправить алгоритм replay. Для «мгновенных кликов» параллельно локализовать работу BB до `openWterm`; одна оптимизация терминального парсера эту задержку не устранит.
